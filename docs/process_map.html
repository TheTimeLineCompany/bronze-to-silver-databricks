Silver Modelling Process Map

Seven phases take one source system from a raw file dump to a deployable silver load. Each phase writes into its own numbered folder and ends with a checkpoint pack. Each step shows what the agent does, what code guarantees, and what a human decides. Red slips are checkpoints: a person approves them in a pull request, and can send feedback that reruns the steps before it.

Focus funnel for the input dump

The agent never reads 00_inbox as a whole. Code makes the dump small first; the agent then reads only named parts, and from P2 on it works from the brief and the evidence register. Numbers are from the S07 example.

00_inbox — every file as delivered: overviews, profiling workbooks, drafts, copies, emails, logos11 files
Inventory (code) — duplicates and version groups found, type suggested1 duplicate · 2 old versions
Triage — core / supporting / background / ignore4 / 1 / 2 / 4 · max 15 core
Read plan — only named sheets, pages, sectionse.g. sheet LEGS only
Evidence register — one short claim per fact, with origin and confidence9 document claims · ≤40 words
Source brief — the page every later step reads158 words · ≤1800

Confidence rules

Client profiling workbooks carry their own labels (High, Amber, 40%…). Code normalises them; the rules decide what each level may support.

highUsable alone, unless bronze contradicts it. Labels: High, H, green, ≥ 80%.
mediumNeeds one corroboration: bronze, or a second document with authority ≤ 3. Amber, 50–79%.
lowHypothesis only. Verify in bronze or ask the client before it supports a key, FK, grain, or rule.
unknownNo label. Treated as low.

Bronze wins for structure (keys, nulls, formats). Documents win for meaning (definitions, rules, codes). A client answer wins for both. The STTM validator refuses a PK, BK, FK, or business-logic column that rests only on low or unknown evidence.

Bronze discovery: code does the work, agents decide the rest

The largest piece of P2. Code finds keys, links, and roles with numbers as proof, on samples and with exact checks only for candidates. Judgement goes on small cards. Genie Code has no documented sub-agents, so each card is a self-contained task that any runtime can answer.

StageRunsWorkOutput
catalog + metacode, oncetables, columns; Unity Catalog comments, owners, tags, masks, declared PK/FK, statistics, history; lineage system tables (who writes and reads)parts/catalog.json, metadata/, lineage_view.json

Runtimes for cards: a Genie Code chat per card, or tools/discovery/card_runner.py (one fresh LLM call per card on a serving endpoint, answers checked), or later a Databricks multi-agent app / Agent Bricks supervisor with the card runner as a tool. Method: data-profiling literature (Abedjan, Golab, Naumann) and Kimball's grain and table roles.

Your input at every start and every review

The process is interactive. At the start of each checkpoint, and each time you type an instruction, give feedback, or upload a file, the input goes through the same four steps before any work starts.

typed or uploaded→checked against the ontology→clarify: a few questions→route: steps that use it
StepWhoWhat happens
Captureyou, in 00_start_heregive-instruction (IN-xxx, for a step or all), give-feedback (FB item), or files in uploads/ + register-uploads (instruction, feedback, or handover to the next stage). A filled scope sheet is applied directly.
Checkcode: x_input_ontology.pyEvery term is matched to the business layer (objects, synonyms, abbreviations, relationships, rules), the data layer (classes, load patterns, bronze and silver tables and columns), and the information layer (phases, steps, checkpoints, evidence, questions). File headers and sheet names are read; values are not. Result: matches, unknown names, new concepts, conflicts (with instructions, evidence, relationships, business rules), intent, and route.
Clarifyagent: @x-clarifyAsks at most 7 questions, and only about unknowns, new concepts, conflicts, an unclear intent, or a rerun of approved work. A clear, known, conflict-free input gets no questions. "I don't know" becomes a client question.
RoutecodeAnswers become instructions, evidence (team_knowledge, medium), feedback, client questions, or CP3 change requests. The input gets its route: the first step that uses it, and the checkpoints that go back to pending.

Feedback and rerun at any checkpoint

A reviewer does more than approve or reject. One feedback item FB-xxxx.yaml in 06_feedback/<checkpoint>/ can mix any of the kinds below. Code works out what to rerun, sets later checkpoints back to pending, and keeps the checkpoint blocked until the reviewer verifies the change.

open→in_progress→ agent reruns →applied→ reviewer checks →verifiedorrejected

Red states block approval of their checkpoint. Only the reviewer sets verified or rejected. Every agent run is logged to run_log.jsonl.

Upstream issues: an agent in a later phase finds a problem
agent raises→proposed→ person accepts →open→ same loop as above

The item sits on the earlier checkpoint that owns the problem and blocks the agent's own checkpoint (--blocks). The agent does not work around it. The third attempt for the same problem stops the gate: a person decides. All items: registry/board/feedback_board.html.

Ontology: three layers, one chain

The ontology keeps 30 sources coherent. Every silver table names a business object and a data class, every FK follows a business relationship, and every column traces down to evidence and its origin.

Layer 1 · business.yaml

Business

  • Domains: PROC, COST, LOGI, SAVE, ORG
  • Processes, e.g. P-LOGI-02 track container legs
  • Business objects + synonyms (Supplier ← vendor, provider)
  • Relationships R01–R17 with cardinality
  • Business rules BR-xxx-nnn (CP4b)
Layer 2 · data.yaml

Data

  • Data classes: master, reference, event, agreement, measure, snapshot, bridge
  • Allowed load patterns per class
  • Conformed classes = shared entities
  • Key types BK, SK, FK; grain rule
Layer 3 · information.yaml

Information

  • Document types with authority
  • Relevance + reading rules + budgets
  • Evidence origin, confidence, status
  • Phases, checkpoints, handovers
